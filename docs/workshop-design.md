# Workshop Design

> **Heartbeat.** Naming pass complete (see `docs/decisions.md`) — this doc was drafted after the name was chosen, so it uses the final name throughout.

## The one-line problem

Agent-literate practitioners who've already learned Rust the agent-native way (via `borrow-native` or equivalent) hit a second wall: distributed systems is a subject where almost nothing compiles wrong, yet almost everything can still be wrong — a correct-looking Raft implementation can pass every unit test and still lose committed data the first time a network partition heals badly. This workshop's bet is that the fix isn't more reading (MIT's own 6.5840 course material is excellent and freely available), it's a **deterministic gate that can actually see network faults**, not just type errors, paired with an agent-native harness and Coachgremlin's conceptual layer on top.

**Reseeded 2026-08-29, after a staff-engineer-level critique of the first design:** the original arc built a generic, unnamed "sharded key-value store" — the single most well-trodden vehicle in every distributed-systems course that exists, including 6.5840 itself, and one with zero thematic connection to this workshop's own audience. Every module now builds one real product instead: **Checkout**, a distributed lock/session-ownership service. This isn't an arbitrary reskin — it's the exact shape of a real problem this factory's own `git-contract.md` already documents (don't let two concurrent agent sessions yank a shared branch or worktree out from under each other; use a linked worktree instead, since two sessions can't safely hold the same branch at once). Checkout is that coordination primitive, built from scratch: `Checkout(resource, holder, lease_duration)` grants exclusive, time-bounded ownership; `Renew` extends it; `Return` releases it early; a lease that's never renewed expires on its own, so a crashed holder doesn't lock a resource forever.

## Audience

Agent-literate practitioners: comfortable with git, the CLI, driving a coding agent daily, and already fluent in Rust specifically (ownership, borrowing, traits, `async`/await — the level `borrow-native` teaches to). **Not** a Rust-fundamentals workshop and **not** a true-beginner distributed-systems course — the one thing assumed unfamiliar is distributed systems itself: consensus, replication, partition tolerance, and what a network can actually do to a running protocol.

## Format

Self-paced, public repo. Matches `terminal-velocity` and `borrow-native`'s precedent.

## Subject vs. method (see `<hekton-machinery>/gremlins/workshop/workshop-gremlin.md`'s "Variant: Tech/Language Workshops")

- **Subject:** distributed systems — RPC over unreliable networks, single-node service design, leader election, log replication, persistence, log compaction, replicated state machines, and sharding.
- **Method:** agent-native — every module's core exercise runs through the learner's own coding-agent harness, graded first by a **deterministic check** (a real Raft implementation tested against real, simulated network faults), then by Coachgremlin's conceptual feedback on top.

The hook is the same shape as `borrow-native`'s, extended: "let a simulated, adversarial network — not an opinion — be the first gate." That claim leans on the multi-seed deterministic-tier design in "The deterministic gate, in the two-tier vocabulary" section below — a single arbitrary seed can get lucky the way a compiler never does, which is why that section makes "green across a published seed set" the standing requirement rather than "green once."

## The shared project: `Checkout`

Added 2026-08-29, reseeding the arc around one real product instead of a generic KV store, the same shape decision `borrow-native` made when it retired a standalone toy exercise in favor of `relay`. **This deliberately doesn't copy `relay`'s exact shape**, and that difference is worth stating rather than silently diverging: `relay` adds one real feature to the same running project every single module, because Rust's own concept arc (ownership → borrowing → ... → async) is a chain where each concept is genuinely needed to build the next feature. Raft's own protocol modules don't have that property — leader election, log replication, persistence, and log compaction are generic consensus mechanics that don't know anything about locks or leases; they replicate opaque log entries for *any* application built on top. Forcing Checkout-specific busywork into those modules would misrepresent how real systems are actually layered (this is exactly how 6.5840 itself is structured: Lab 3's Raft is generic, Lab 4's KV service is the specific application on top). So Checkout's own build-out is honestly uneven, not evenly spread:

| # | Module | What it adds to `Checkout` |
|---|---|---|
| 01 | RPC Over an Unreliable Network | The RPC layer itself, exercised with Checkout's own message shapes (`CheckoutRequest`/`CheckoutResponse`: resource, holder, lease duration) even though no real checkout logic exists yet — the first appearance of the domain type every later *`Checkout`-facing* module (02, 07, 08, 09) builds on, not Modules 03-06, which are deliberately domain-agnostic |
| 02 | A Single-Node Checkout Service | The real `Checkout`/`Renew`/`Return`/`Status` API against a single in-memory node: exclusivity, lease expiry, no replication yet |
| 03-06 | Raft: Leader Election, Log Replication, Persistence, Log Compaction & Snapshots | The generic Raft engine `Checkout` will run on in Module 07 — deliberately not Checkout-specific; connective narrative in each module names what this engine will eventually carry |
| 07 | Fault-Tolerant Checkout Service on Raft | Module 02's API wrapped in Module 06's Raft engine: checkout/renew/return/status requests replicated, surviving a leader failover mid-request |
| 08 | Sharded Checkout Service | Resources partitioned by namespace (e.g., which repo, which branch) across many replica groups, so the service scales to a large fleet of concurrent agent sessions |
| 09 | Synthesis capstone | A real, seeded bug in the accumulated `Checkout` service — diagnose the root-cause concept, fix it |

**Revised 2026-08-29, fourth pass, after three doubt-driven-development cycles** (single-model + Codex cross-model in cycles 1-2; single-model only in cycle 3, by explicit human choice): the table above describes *what* each module adds, but `Checkout`'s own hardest correctness properties were left unstated in the first draft, the cycle-1 fix had internal-consistency bugs cycle 2 caught, and cycle 2's own fix had five more real problems cycle 3 caught — a dedup key that breaks under this service's own mainline usage pattern, a snapshot gap for fencing tokens on now-free resources, a genuine logical contradiction in how group-level state was described as migrating per-resource, terminology drift, and an unstated unit relationship between wall-clock lease durations and the logical clock. This is the corrected result, not any earlier draft. Stopped at three cycles, the process's own ceiling — see the closing note below.

1. **The replication discipline that matters is leader-proposes, followers-never-read-their-own-clock — not "runs on turmoil."** Corrected cycle 2 (both reviewers flagged the prior wording as conflating the test harness with the product): the leader proposes a logical timestamp into the log on every committed operation; followers compute expiry only from the latest *committed* timestamp, never an independent local clock read. The test harness happens to drive this clock via `turmoil`'s virtual time so it stays deterministically testable — that's an implementation choice for Coachgremlin, not the invariant itself. **Units, added cycle 3** (single-model reviewer: the prior drafts never related this timestamp to `lease_duration`'s own wall-clock units): the leader's proposed timestamp is real-time-equivalent (milliseconds since an epoch), sourced from the leader's own clock — real wall-clock in a hypothetical production deployment, `turmoil`'s virtual clock in the test harness — never from a follower. This is consistent with, not a violation of, this property's own rule: only the leader ever reads a clock at all.
2. **The replicated clock must advance even without client traffic, or expiry never fires.** Added cycle 2 (both reviewers independently found this): if a timestamp only advances when a client operation commits one, an untouched resource's lease looks perpetually valid forever, since nothing ever proposes a later time. The leader must periodically commit a clock-advancement entry on its own, independent of client operations (e.g., piggybacked on Raft's own heartbeat).
3. **A new leader must never propose a timestamp lower than the highest one already committed.** Added cycle 2 (Codex): a real risk specifically after a leadership change or a partition healing — a stale or reconnecting leader proposing backwards time would violate the entire "deterministic function of replicated state" premise.
4. **Every `Checkout` call returns a lease generation to the caller; every subsequent `Renew`/`Return` call is keyed by `(resource, holder, generation)`, not just `(resource, holder)`.** Corrected cycle 2 (both reviewers): the prior draft required generation-checking but never specified `Checkout` actually returns the generation, and its own prose still wrote `Renew(resource, holder)` — without the generation flowing through the API, the fencing requirement (a stale command against an already-superseded lease must be rejected) isn't enforceable at the boundary that matters.
5. **Request-ID deduplication uses `(client_id, resource, monotonic sequence number)`, not a bare opaque ID — the bounded structure MIT 6.5840's own Lab 4A actually uses, not just cites.** Corrected cycle 2 (both reviewers): a bare per-call ID gives no way to know when it's safe to forget a dedup entry, so the table would grow unboundedly for the service's lifetime. A monotonic per-client-per-resource sequence lets the server keep only the highest sequence and its response per `(client, resource)` pair. **Corrected again cycle 3** (single-model reviewer, a real bug in the cycle-2 fix): keying by `client_id` alone, without `resource`, breaks under this service's own mainline usage — a client holding two independent leases and renewing both concurrently would have the second renewal's sequence silently overwrite the first's cached entry, since only one "highest sequence per client" was kept regardless of which resource it was for. The sequence number is scoped per `(client, resource)`, not globally per client.
6. **A deduplicated response caches the exact outcome — granted, denied, or the specific error, generation-stamped — and replays it identically on retry.** Added cycle 2 (Codex): treating denials differently from successes under dedup is a real trap (a retried denial could wrongly flip to granted, or wrongly stay denied forever after the resource became available). Cache and replay the same outcome either way.
7. **Every resource's generation counter is persisted state independent of whether it currently has an active lease — not just "generations of active leases."** Corrected cycle 2 (both reviewers): a snapshot that resets a generation counter or drops the dedup table on restore reopens exactly the bugs items 4-6 exist to close. **Corrected again cycle 3** (single-model reviewer, a gap in the cycle-2 fix): "active leases, generations" only covers currently-held leases — a resource that's been returned or expired has no active lease, so nothing recorded "the last generation this resource ever issued." If the log later compacts past that resource's last operation, the next `Checkout` has no record of what generation to issue past, and could reissue an already-used one. The snapshot contract is: every resource that has ever had a generation issued keeps that counter, active lease or not, plus the request-ID dedup table.
8. **Lease state (holder, generation, expiry timestamp) moves with its resource during Module 08's shard migration; the destination group's own clock must have already advanced past the migrated resource's last committed timestamp before the migration is considered complete.** Corrected cycle 2 (both reviewers flagged the sharding interaction was unaddressed), then corrected again cycle 3 (single-model reviewer, a real logical contradiction in the cycle-2 wording): the prior draft said "the logical clock" and "the dedup table" move with the resource, but neither is actually resource-scoped state by this section's own definitions — the clock belongs to the whole Raft group (every resource in that shard shares it), and item 5's fix above now scopes the dedup table per `(client, resource)`, which *is* resource-scoped and does migrate cleanly. The clock doesn't transplant; instead, the destination group (which already has its own running clock) must confirm its clock has caught up to at least the source's last known timestamp for that resource before serving requests against it.
9. **Linearizable reads use read-index (or routing through the log) — never leader-lease-read.** Corrected cycle 2 (single-model reviewer): leader-lease-read is a legitimate Raft optimization in general, but it fundamentally depends on bounded real-clock skew between nodes to safely skip a heartbeat round-trip, which would reintroduce exactly the wall-clock dependency items 1-3 exist to eliminate, just at the Raft-leadership layer instead of the lease layer. Not an acceptable choice for this design, even though it's a real option in general Raft-based systems.
10. **Initial `Checkout`'s `lease_duration` is client-requested but server-capped to a stated maximum.** Added cycle 2 (Codex): without a cap, the same abuse this design already prevents at renewal (an unbounded hold on a resource) reappears at the initial grant.

**Also fixed:** resource identifiers are opaque, canonical strings, canonicalized once at the API boundary before any routing or exclusivity check runs — the exclusivity key and Module 08's shard-routing key are derived from that *same* post-canonical value, not independently parsed, or aliasing (`main` vs `refs/heads/main`, case differences) could let two sessions bypass the lock entirely by naming the same resource two different ways. Module 07's build-out is not entirely free of this section's additions, despite the arc table above describing it as unchanged: Module 07's retry-handling layer must reuse the exact same `(client_id, resource, sequence number)` tuple from item 5 on a retry, not mint a separate "request ID" of its own — **corrected cycle 3** (single-model reviewer): the first version of this fix used the term "request ID" here and "sequence number" in item 5 as if they were two different things, exactly the kind of terminology looseness cycle 2 already flagged once elsewhere in this section. One term, one mechanism.

**Explicitly named, not deferred to silence:** the capstone (Module 09)'s bug-injection and grading mechanism needs a real bypass-prevention story before it's authored, not a generic "TBD" — this factory has direct, evidenced history with checker-execution-bypass patterns (a shadow-module planted in the working directory, or an exit-code short-circuit, defeating a checker that only inspects a process's return code). Minimum bar, stated now rather than left as a pure warning: the capstone's fix-verification must run in a directory the learner's own solution cannot introspect or write shadow modules into, must verify a real pass *count* against both the practice and held-out seed sets specifically (not just "the full seed sets" ambiguously, and not a bare process exit code that a zero-tests-collected run could satisfy vacuously) — **strengthened cycle 3** (single-model reviewer, closing a vacuous-pass loophole and an ambiguity about which seed sets grading actually exercises). The full grading design is still Coachgremlin's job.

**Doubt-driven-development stop condition, named explicitly:** stopped at three cycles — the process's own ceiling. Cycle 3 (single-model only, Codex skipped by explicit human choice) still surfaced five real, substantive, non-repeat problems in the cycle-2 fix, which is itself information: this section has now had three real rounds of correction, not one confident draft, and per the process's own guidance, a fourth cycle would mean grinding rather than converging — the honest next test is Coachgremlin's real content-building dry runs against actual code, the same discipline this document already commits to for the deterministic-gate design elsewhere. Implementation-level specifics (exact dedup-table garbage-collection policy, exact snapshot binary layout, full capstone grading implementation) remain explicitly deferred to that phase, consistent with this document's own stated scope boundary.

**Correction, 2026-08-29:** this workshop was originally scoped, informally, with the arc "RPC → leader election → log replication → a KV store on top → sharding" — implying the KV interface comes *after* Raft is built. 6.5840's real current lab order says otherwise: **Lab 2 builds an unreplicated, single-node KV service before Raft exists at all** (Lab 3), and only then wraps that same KV interface in Raft (Lab 4). The pedagogical reason is straightforward once seen: it separates "design a correct KV API" from "make that API survive a partition," so a learner debugging Lab 4 already knows the KV interface itself is correct and can attribute every remaining bug to the replication layer. This workshop's module arc (below) follows the real order, not the original guess.

**`labrpc`, the course's own deterministic-gate harness** ([pdos.csail.mit.edu/6.824/labs/lab-raft1.html](https://pdos.csail.mit.edu/6.824/labs/lab-raft1.html)): a Go RPC package the test harness uses to delay, re-order, and discard RPCs to simulate network failures, plus (confirmed via Lab 3C/3D's persistence-across-reboot requirements) crash and restart individual servers mid-test. **The Raft paper itself:** Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm (Extended Version)" (2014), linked directly from the lab page as `raft-extended.pdf`. The lab's own instructions cite it by section: Figure 2 (the "Summary of Raft" — state variables and the RequestVote/AppendEntries RPC definitions every implementation is checked against), Figure 4 (the actual server-state transition diagram: Follower → Candidate → Leader), §5.2 (election timeouts), §5.4.1 (election restriction), §7 (log compaction), Figure 13 (the snapshot/InstallSnapshot RPC). This workshop uses the same paper as its own primary reading, module by module, rather than re-deriving Raft from a secondary source.

**Course-wide reading list** (from the schedule, for context on what this workshop deliberately does *not* cover): MapReduce (2004), GFS (2003), Paxos, Raft (2014), a linearizability paper, ZooKeeper (2010), Spanner (2012), Chain Replication (2004), FaRM (2015), IronFleet (2015), Memcached at Facebook (2013), AWS Lambda container loading (2023), Ray (2021), SUNDR (2004), Bitcoin (2008), Practical BFT (1999). This workshop is Raft-centric and deep (a deliberate scope decision, see below) — it does not attempt Paxos, BFT, or the systems-survey breadth of the full course.

**Differentiator against 6.5840 itself:** none of what follows is a claim that this workshop out-teaches a real MIT course taught by course staff with real grading infrastructure. Two differentiators are already true by construction: a **Rust implementation** (6.5840 is Go-only) and **agent-native delivery** (6.5840 assumes a human alone at a terminal). Two more are **stated intent, not yet built or evidenced** — flagged explicitly, the same honesty discipline `borrow-native` applied to its own teaching-method claims: **Coachgremlin's conceptual tier** is intended to catch what 6.5840's pass/fail tester structurally can't (a learner passing every test with a Raft implementation a real reviewer would reject), and a **keepable takeaway per module** is intended to leave the learner with an artifact, not just a grade — both are Coachgremlin's job at content-building time, not yet demonstrated. 6.5840's own labs and lecture notes remain the primary source of truth for the protocol itself; this workshop does not attempt to replace them.

## Existing Rust prior art (research pass, 2026-08-29)

- **`openraft`** ([github.com/databendlabs/openraft](https://github.com/databendlabs/openraft)) — a real, actively maintained, production-grade Rust Raft library, derived from the earlier `async-raft` project with a documented set of correctness fixes ([derived-from-async-raft.md](https://github.com/databendlabs/openraft/blob/main/derived-from-async-raft.md)). It's the consensus engine behind Databend's meta-service cluster: async/event-driven (no periodic ticks), generalized joint-consensus membership changes, fully pluggable storage/network. **This is a production library, not a teaching resource** — no tutorial arc, no graded exercises. It's this workshop's honest answer to "why not just use a library": because the point is understanding Raft well enough to *know* when `openraft` is the right call later, the same relationship `borrow-native` has to the Rust Book (a resource this workshop stands alongside, not against).
- No widely-known "6.824/6.5840 ported to Rust" community course surfaced in this research pass. Worth stating as "not found," not "doesn't exist" — a gap this workshop can genuinely fill if true, an honest unknown if it just wasn't surfaced.

## The deterministic gate: `turmoil`

**Dependency decision, human-confirmed 2026-08-29** (per this repo's `dependency_changes: human_required` governance gate): this workshop adopts **`turmoil`** ([docs.rs/turmoil](https://docs.rs/turmoil/latest/turmoil/)) as its Rust equivalent of `labrpc`, rather than hand-building a network-simulation harness from scratch.

- **What it does:** runs many simulated hosts deterministically on a single thread. One seeded RNG drives every scheduling and delivery decision, so a failing seed reproduces exactly. It supports dropping packets, partitioning hosts, injecting latency, reordering segments, and killing a connection mid-stream — a near-exact match for `labrpc`'s delay/reorder/discard, plus explicit partition support `labrpc` itself provides via its own `config.go` connect/disconnect calls.
- **Why not `madsim`** (the other real, current option — the "Magical Deterministic Simulator," used in production by RisingWave): `madsim` goes further, achieving determinism by substituting shim crates (`madsim-tokio`, a patched `getrandom` backend, etc. via `cfg(madsim)`) so `Instant::now()`/`getrandom` stay deterministic *for code built against those shims* — not by transparently intercepting arbitrary code the way a generic `libc` hook would. That's real integration cost (every dependency in the fault-injected path needs a madsim-aware build) this workshop doesn't need to pay yet — Raft's own timing (election timeouts, heartbeats) is expressible entirely through Tokio's mocked time, which `turmoil` already covers without any crate substitution. Escalating to `madsim` stays an option if a later module (sharding, most likely) hits a case `turmoil` can't simulate.
- **Con of not adopting either:** hand-rolling this harness means its own bugs are indistinguishable from a learner's Raft bugs when a test fails mysteriously — exactly the failure mode a deterministic gate exists to prevent. Building one from scratch also means re-solving a problem `turmoil` already solves, for a piece of infrastructure that isn't this workshop's actual teaching content.

## The module arc

Anchored to 6.5840's real lab order (corrected above), scoped for a learner who already knows Rust — modules that would be Rust-fundamentals review for this audience are skipped entirely; every module here is genuinely new (distributed-systems) content. Each module names its **hard prerequisite** explicitly, per the Workshop Gremlin's concept-dependency-arc requirement.

| # | Module | Hard prerequisite | 6.5840 anchor | Gate's named fault scenario (deterministic tier) |
|---|---|---|---|---|
| 01 | RPC Over an Unreliable Network | none (Rust fluency assumed) — **but see the callout below: this is not a warm-up** | "RPC and Threads" lecture; `labrpc`'s own role, reimplemented as this workshop's `turmoil`-backed harness | The harness itself, under test: dropped/delayed/reordered `CheckoutRequest`/`CheckoutResponse` messages arrive exactly as configured, across both seed sets |
| 02 | A Single-Node Checkout Service | 01 (needs the RPC layer to expose a service at all) | Lab 2 — deliberately unreplicated; the interface this whole arc eventually wraps in Raft | Concurrent checkout requests against the single-node service under injected latency/reordering never grant the same resource to two holders at once, and every lease correctly expires |
| 03 | Raft: Leader Election | 01 (RPCs) | Lab 3A; Raft paper §5.2, Fig. 2, Fig. 4 | A `turmoil` partition isolating the current leader; exactly one new leader is elected in the majority partition, never two leaders in the same term |
| 04 | Raft: Log Replication | 03 (a leader must exist before it can replicate a log) | Lab 3B; Raft paper §5.3-5.4.1 | A follower that missed several entries catches up correctly after a simulated partition heals, with the log-matching property intact |
| 05 | Raft: Persistence | 04 (persisted state is the log/term/vote Module 04 already produces) | Lab 3C; Raft paper Fig. 2's persistent-state fields | A `turmoil`-simulated crash-and-restart mid-replication recovers exactly the pre-crash persisted state, never re-votes in an already-decided term |

| 07 | Fault-Tolerant Checkout Service on Raft | 02 (the Checkout interface) and 06 (a complete Raft) | Lab 4 | The Checkout service stays linearizable across a `turmoil`-simulated leader failover mid-request — a client never observes a granted lease disappear, nor a denied checkout silently become granted |
| 08 | Sharded Checkout Service | 07 | Lab 5 | A shard migration in progress, combined with a simulated partition on the source or destination group, never leaves a resource owned by zero or two groups at once |
| 09 | Synthesis capstone | all of the above | — | A real, seeded bug in the accumulated `Checkout` service spanning 3+ concepts from the arc — the learner must get every module's `turmoil` suite green again (deterministic tier) *and* correctly diagnose, in writing, which arc concept was the actual root cause before fixing it (conceptual tier), mirroring `borrow-native`'s own capstone shape |

**Module 01 is not a warm-up.** Flagged directly per this workshop's own Review Panel (`docs/review-panel/2026-08-29-initial-design.md`, End-User/Learner persona): "no prerequisite" describes the *concept* dependency, not the *engineering* difficulty. Module 01 is where the learner builds the `turmoil`-backed harness every later module's gate depends on, with zero distributed-systems intuition yet — closer to this workshop's hardest onboarding ramp than a gentle first step. Content-building should treat it accordingly (more scaffolding, not less).

### Why this order

Modules 03-06 are 6.5840's own Raft parts kept in their original order rather than re-split — Ongaro & Ousterhout's paper and the lab's own structure already argue for leader election before replication (nothing to replicate without a leader), replication before persistence (persistence exists to survive a crash mid-replication), and persistence before compaction (compaction discards persisted state, so the thing being discarded has to be reliably saved first). Module 02 sits before Module 03, matching 6.5840's real order and this design doc's own correction above: building `Checkout`'s interface without replication first means every bug surfaced in Module 07 is attributable to the Raft layer, not the API design — worth being honest that this is a debugging-attribution argument, not a hard technical dependency the way 03→04→05→06 are (Module 03 doesn't actually require Module 02's code to exist; it's building the generic Raft engine `Checkout` will only sit on top of starting Module 07, per "The shared project" section above). Module 08 (sharding) is last among the core modules because it assumes a working replicated `Checkout` service to shard in the first place.

## The deterministic gate, in the two-tier vocabulary `borrow-native` established

**Revised 2026-08-29, fourth pass, after three doubt-driven-development cycles** (single-model + Codex cross-model each cycle, stopped at the cycle ceiling with real findings still surfacing — see the closing note below): the first version required "green across a fixed, published set of seeds." Cycle 1 found that framing overclaimed what a fixed, published set can prove. Cycle 2 found the fix itself had two real bugs and that the corrected framing still overclaimed what any finite seed testing proves. Cycle 3 found a real technical error (a wrong Raft safety-property example), a forward-compatibility bug (a persisted-state check that would fail Module 06), a missing liveness fairness assumption, and confirmed the resubmission-oracle gaming risk is narrowed, not closed. This section is the result of all three cycles, not any single draft.

**Point 2 superseded 2026-08-30, after a separate three-cycle doubt-driven-development process (Phase A.8 of `docs/completion-roadmap.md`; single-model cycle 1, single-model + Codex cross-model cycle 1, single-model cycles 2 and 3):** the "held-out grading set" model below assumed a trust boundary — Coachgremlin as a party separate from the learner, capable of holding a secret from them — that this workshop's own documentation elsewhere states doesn't exist (Coachgremlin is "a role you run yourself," typically the same learner or the agent they're directing, run locally). Cycle 1 (plus Codex, independently convergent) found the first proposed fix — a nonce chosen by the grading script from wall-clock time or OS randomness, fed into a public generator — gave the learner nothing to overcome: since the generator is public and pure, every candidate nonce can be enumerated entirely offline with zero cost. Cycle 2 found the next fix — a nonce derived from a hash of the solution's file bytes — left the resulting transcript unverifiable by a third party (a hash is one-way; nobody receiving it can check what code actually produced a claimed result), understated how cheaply that hash could still be searched (pure hashing of trivial behavior-preserving edits, no compilation or test run needed for the search phase itself), and surfaced several smaller gaps (only per-bucket seed distinctness, an unspecified hash encoding, no enforced floor arithmetic, recorded-but-unverified version pins, a deletable attempt log, unstated file-hashing edge cases, and the capstone module being the easiest to grind under this scheme — the opposite of what its stakes call for). Cycle 3 confirmed the resulting fix (below) actually delivers its central claim — a git tree hash is genuinely immune to the commit-metadata grinding a plain commit hash would have permitted — but found one more real, critical gap (nothing tied the recorded hash to what was actually executed) plus several precision gaps (mode/rename/symlink grinding, line-ending canonicalization, a version-pin residual, minor terminology and encoding issues). All fixed or explicitly named below; stopped at the cycle-3 ceiling per the same discipline the original gate design used.

1. **Deterministic tier (primary), what it actually claims.** `cargo test` green across a module's seed sets (below) means the implementation resisted every targeted fault schedule tried against it — it is not, and cannot be, a proof that the implementation is correct with respect to the module's target Raft property. Testing shows the presence of bugs the seed sets were built to find, never the absence of every bug. This tier's real job is narrowing the space of plausible-but-wrong implementations as far as a testing budget allows, not certifying correctness — a reframe from this section's first two drafts, both of which overstated this as "mechanically distinguishing correct from lucky."
2. **Grading draw, not a held-out secret** — the practice set stays, the held-out set doesn't. **"Held-out" is retired entirely as a security mechanism, with no informal exception** (a Phase A.8 finding: the term risks reintroducing the trust-boundary framing by habit even after the mechanism changes). Two things exist now:
   - **Practice set** — unchanged in spirit: small, fixed, published, used for fast local iteration during development (e.g., Module 01's existing `SEEDS = [1, 2, 3, 5, 8]`). Disjoint from, and never counted toward, the grading draw below. Passing the practice set is never itself a grading criterion.
   - **Grading draw** — computed fresh from the solution actually under test, not published in advance and not fixed forever, but not secret either: the mechanism that produces it is fully public.
   - **Nonce = the git tree hash of the exercise's solution path**, obtained via `git rev-parse HEAD:<solution-path>` (or equivalent) against the learner's own repository — **not** the commit hash. This distinction is load-bearing, confirmed in cycle 3: a commit object's hash covers author, committer, message, timestamp, parent, and optional signature, all of which cost nothing to change (`git commit --amend` in a loop, touching zero real content) — using it as the nonce would have made grinding a favorable draw *cheaper* than the rejected file-hash approach, not harder. A tree object covers only entries' names, modes, and blob hashes for files under that path, so metadata-only edits cannot change it. The solution path must be a directory (matching every module's actual fixture layout, e.g. `fixtures/checkout/`), guaranteeing a genuine tree object rather than a single blob. This assumes the repository's default SHA-1 git object format; a future migration to SHA-256 objects is a generator-version bump (below), requiring the same revalidation a `turmoil` version bump already does.
   - **Recorded separately: `commit_sha`**, the current `HEAD` commit, kept purely as a retrieval pointer so a third party can `git show`/`git archive`/`git checkout` the actual solution and independently re-run grading — never used as an input to seed derivation itself.
   - **Grading must run against a clean checkout of that exact commit, not the live working directory** — cycle 3's critical finding: without this, a learner could commit a version of the solution that hashes favorably, then edit the working tree afterward before actually running the tests, and the recorded `tree_hash`/`commit_sha` would describe code that was never executed, silently reopening the same unverifiable-transcript problem cycle 2 found. Grading fails closed (refuses to emit a transcript marked canonical) if `git status --porcelain -- <solution-path>` is non-empty, mirroring the version-pin fail-closed behavior below.
   - **Generator:** `seeds_for(module_id, tree_hash, dimension_combos: &[ComboId], min_per_combo: usize) -> Vec<(ComboId, u64)>`. For each of a module's published, named fault-dimension combinations (point 9), derive `min_per_combo` (>= 5) seeds via BLAKE3 over a fixed, unambiguous byte encoding — each of `(module_id, tree_hash, combo_id, index, combo-processing order)` length-prefixed and concatenated in a stated fixed order, reduced to a u64 via the first 8 bytes big-endian — incrementing `index` and rehashing on any collision against a **single set tracked globally across all combo buckets for that draw**, not per bucket. The generator asserts/returns an error if the total draw count falls below 50 — a checked runtime invariant, not just documentation; Coachgremlin's per-module content-authoring checklist must separately confirm `combo_count * min_per_combo >= 50` before a module ships.
   - **Pass criterion:** grading passes iff every drawn seed passes. No partial-credit threshold — stated as an accepted trade-off, not an oversight: an all-or-nothing bar over a thin (5-per-combo) floor increases the value of finding even one favorable draw via the residual named below, and full diagnostics (next bullet) sharpen a learner's ability to target that search. Named, not resolved, matching how point 9 already names its own specificity-vs-gaming-resistance tension.
   - **Full diagnostics may be shown on every run** — which seed failed, what schedule, what assertion — no pass/fail-only restriction, since there is no external party whose test coverage needs protecting from disclosure.
3. **Grading transcript, version pinning, and the residuals this design does not close.** A grading transcript must record: `module_id`, `tree_hash`, `commit_sha`, the exact `dimension_combos` and `min_per_combo` used, `generator_version` (hash function, byte encoding, combo-processing order, and stratification algorithm, versioned together), the `turmoil` crate version and Rust toolchain version actually observed, and per-seed pass/fail results — not merely an aggregate. Grading fails closed (transcript marked non-canonical, not trusted as a valid claim) if the observed `turmoil`/toolchain version doesn't exactly match the repository's own `Cargo.lock`/`rust-toolchain.toml` pins. **Two residuals, named precisely rather than glossed over:**
   - **Grinding remains possible, and is not merely "many real test runs" — it can be cheaper than that.** A learner can obtain a different draw via any change to the tracked file tree that doesn't change behavior: a comment, dead code, reformatting, a file mode change (`chmod +x`), a rename, or a symlink swap — none of which require compiling or running anything to search over, since the seed-derivation hash is public, fast, and pure; only a promising candidate needs an actual test run to confirm. Line-ending/whitespace filters (`core.autocrlf`, `.gitattributes`) are part of the same surface and need the repository's own line-ending behavior pinned for a given logical file to hash consistently across contributors' machines. This residual is not solved here; the stated backstop is Coachgremlin's separate conceptual tier (below), which exists specifically to catch implementations that pass every mechanical test but wouldn't survive real review.
   - **A self-administered version-pin check only catches accidental drift, not deliberate selection.** The fail-closed check above confirms the learner's environment matches *their own repository's* pins — but the learner can edit those same pin files, including choosing a specific `turmoil`/toolchain version because it happens to contain a bug or ordering quirk that hides theirs. Local, self-run transcripts should be understood as a development/practice signal, not a stronger one. The one thing that does close this residual: running the same grading procedure through the canonical upstream repository's own CI (`.github/workflows/rust-ci.yml`) via a pull request, since the CI's pinned versions aren't the learner's to edit in that context — a transcript worth more weight (shown to a mentor, used as a portfolio artifact) should come from there, not a local run.
   - **Attempt log, honestly scoped:** the grading script appends every invocation's `(timestamp, tree_hash, pass/fail summary)` to a local, append-only log, considered part of "the grading transcript" whenever shown to anyone else. Stated plainly, not implied: this is not a security boundary. A learner with full control of their own filesystem and git history can delete, truncate, or rewrite this log exactly as easily as they could falsify any other local record. It helps an honest-but-self-deceiving learner notice their own pattern of repeated attempts; it does nothing against one willing to also falsify the log.
   - **Reproducibility vs. correctness, stated as distinct:** given `commit_sha`, a third party can retrieve the actual solution and independently verify a claimed pass/fail result — a genuine improvement over the file-hash approach, which could only be checked for internal consistency, not against real code. This still does not establish the implementation is correct beyond the sampled draw; that remains the conceptual tier's job, not this mechanism's.
   - **Generator-version bumps** (a change to the hash function, byte encoding, combo-processing order, stratification logic, or the git object-hash format) require the same re-validation a `turmoil` version bump already requires (point 10) before merging.
   - **Module 09 (capstone), left open on purpose:** hashing the capstone's entire accumulated multi-module solution tree would give a learner the largest, easiest-to-grind file surface of any module — backwards from what its stakes call for. The hashed path's exact scope for Module 09 can't be fixed here for the same reason no module's actual fixture layout beyond Module 01 is specified in this document yet: it depends on content that doesn't exist. Coachgremlin's Module 09 content-authoring pass must choose that scope deliberately (e.g., restricted to files relevant to what's newly graded) rather than defaulting to the whole repository tree — named now so it isn't discovered late.
4. **A seed's outcome must never vary across reruns — and if it does, that is a failure of the harness, not a reason to add more seeds.** Fixed 2026-08-29 (cycle 2 finding: the first version of this bullet had this backwards). In a genuinely deterministic setup, replaying the same seed reproduces the same schedule and the same result, always. Inconsistent reruns are direct evidence of an uncontrolled nondeterminism leak in the harness or the implementation under test — that must be found and fixed before the seed set can be trusted at all. Growing the seed set is a separate, deliberate content-authoring decision (see point 8), never a response to flaky reruns.
5. **Liveness failures are bounded in simulated time, not wall-clock time — and only under a stated fairness assumption.** Fixed 2026-08-29 (cycle 2 finding: the first version specified a wall-clock bound, directly contradicting point 6's own determinism requirement — machine load, CI contention, or a slower grading host could flip a result with no change to the implementation). A non-terminating run fails once it exceeds a stated bound of simulated time, event count, or scheduler steps within `turmoil`; a wall-clock bound is only an outer infrastructure watchdog (did the whole sweep hang the CI runner), never a per-seed pass/fail signal. **Added 2026-08-29 (cycle 3 finding):** this bound only applies once the seed's own fault schedule stops actively preventing progress — a permanent partition or unbroken message loss makes non-termination correct, not a bug, consistent with Raft's own liveness only holding under eventual synchrony. A liveness-testing seed's schedule must let the network heal and stay quiet for long enough that progress becomes possible before the bound is measured against it; a schedule that never does that is a bad seed, not evidence of a learner's bug.
6. **Constrain learner code to `turmoil`-controlled nondeterminism only.** No direct calls to real wall-clock time or OS-level randomness (`SystemTime::now()`, `thread_rng()`, or equivalent) — time and randomness must route through `turmoil`'s simulated clock and a provided/injected RNG. Unordered-collection iteration order (`HashMap`, `HashSet`, or equivalent) must never be relied on for anything correctness-sensitive; use an ordered collection or explicit sorting instead.
7. **Assert safety invariants continuously through the run, not just at the end.** **Corrected 2026-08-29 (cycle 3 finding — the prior example was a real technical error, not just imprecise):** Raft's actual safety invariant is *at most one leader per term* — two nodes can legitimately believe themselves leader simultaneously across *different* terms (e.g., a stale leader that hasn't yet heard of a newer election) without anything being wrong; that's expected, not a violation. The property this bullet exists to catch is a transient violation *of that specific invariant* (two leaders in the *same* term, even briefly, before one steps down) that self-corrects before the run ends — checking only final state would miss it. Exact instrumentation points are an implementation-level decision for Coachgremlin's content-building pass, not specified at this design-doc level.
8. **Sizing starts from a stated floor and is validated against evidence, not a vibe — retargeted 2026-08-30 (Phase A.8) at the generator, not a fixed set.** At least 50 seeds per module per grading draw (point 2's `min_per_combo >= 5` across a module's named combos), floor enforced by the generator itself, not just stated here. Since the grading draw is no longer a single fixed, enumerable artifact, the old "grow the fixed set from evidence" discipline no longer has a fixed object to act on — it's replaced by a **validation loop**: a small, fixed, published set of validation tree-hashes, computed from this workshop's own reference-correct and reference-incorrect example implementations (the same `attempt-good`/`attempt-naive-*` fixtures Module 01's own dry run already produced), confirms the generator — across every named dimension combination for that module — makes each reference-incorrect implementation fail and the reference-correct one pass. This is what maintainers validate the generator against, both when a module first ships and after any generator-version bump (point 2's residuals). **Caveat, named honestly, carried forward unchanged:** testing only against implementations this workshop itself thought to construct as wrong risks re-creating the "known schedules" problem one level up, at the level of known bug shapes rather than known seeds — an open risk, not a closed one, and worth Coachgremlin tracking which bug classes its constructed counterexamples actually cover over time.
9. **Name a fault scenario's real dimensions, not just its label, and vary them together, not one at a time.** "A partition during leader election" is not specific enough to build a seed set against — the dimensions that matter (majority/minority split, timing relative to in-flight RPCs, the healing point, single vs. repeated partitions) need to be named, and a seed set that varies each dimension in isolation without their combinations is shallower than the label implies. **Tension, stated rather than hidden:** naming these dimensions in Coachgremlin's own content helps content quality but also tells a learner exactly which axes to defend against — full specificity and gaming-resistance pull in opposite directions here, and Coachgremlin's content-building pass has to choose a point on that tradeoff, not this design doc.
10. **Pin the exact `turmoil` version.** A seed's meaning is a function of `turmoil`'s internal scheduler; an unpinned version bump can silently reshuffle what schedule a given seed number produces. Full reproducibility also depends on the Rust toolchain version, target platform, and feature flags — `Cargo.lock` pinning `turmoil` itself is necessary, not sufficient; Coachgremlin's content-building pass needs a real policy for what triggers seed-set revalidation, not just this doc naming that revalidation should happen.

**Conceptual tier (secondary, Coachgremlin).** Whether the persisted-field set matches the module's own required durable state is mechanically checkable and belongs in tier 1 as an explicit check — **corrected 2026-08-29 (cycle 3 finding):** the first version of this fix stated that required set as the fixed, universal `{currentTerm, votedFor, log}`, which is only correct for Modules 03-05; Module 06 legitimately adds snapshot metadata (`lastIncludedIndex`, `lastIncludedTerm`) that an exact-match check against the earlier three-field set would wrongly fail. The mechanical check is per-module (the named fields for that module's stage of the arc, stated explicitly when Coachgremlin authors that module's content), not one fixed field set applied everywhere. Coachgremlin's real job: does the learner's written explanation make a falsifiable prediction Coachgremlin can check against actual behavior (e.g., "predict what happens under a fault variant not in the tested seed sets, then verify the prediction"), not just accept plausible-sounding prose. **Named honestly:** an LLM-graded conceptual tier is itself vulnerable to exactly the "plausible explanation bolted on after the fact" failure mode it exists to catch in the learner — requiring a falsifiable, checkable prediction is this section's attempt to reduce that risk, not a claim that it's eliminated.

**Open, stated honestly:** three doubt-driven-development cycles found real, structural problems in this gate design, not just wording issues, across all three passes. The residual risk after this revision is not "an unlucky attempt passing by chance, at lower odds with more seeds" — that framing (from the first draft) assumed more seeds monotonically shrinks risk. If a bug's triggering window is narrow enough, no realistic number of seeds chosen without targeting that window may ever land in it: a **sampling blind spot**, not bad luck, that doesn't shrink just because a set gets bigger. Point 8's falsification-against-constructed-counterexamples discipline is this draft's answer to that risk, and it is itself an open, not-yet-evidenced bet, same as this whole gate design was before any doubt-driven-development cycle ran. A still-stronger check (e.g., property-based seed generation targeting the named dimensions, rather than a fixed set at all) remains an open upgrade path if Coachgremlin's dry runs find this design insufficient for a given module. **A dangling reference, fixed 2026-08-29 (cycle 3 finding):** the prior draft deferred "CI enforcement of the `turmoil`-revalidation policy" to content-building without ever stating what that policy actually is — only its enforcement mechanics were legitimately implementation-level. The policy itself, stated now: a deliberate `turmoil` version bump requires re-running both seed sets against at least one known-correct and one known-wrong implementation per affected module before the bump is merged; if either result changes, the seed sets need re-targeting, not just re-running.

**Explicitly deferred to Coachgremlin's content-building phase, not resolved at this design-doc level:** per-seed process/state isolation mechanics (the requirement that each seed starts from pristine state is load-bearing and stated above; the exact mechanism is not), a full threat model for what learner code can observe about its own grading context, whether disjoint seed *values* also guarantee meaningfully distinct schedules, whether the conceptual tier's falsifiable-prediction variants need their own rotation policy analogous to point 2's generator-version bumps, the full list of nondeterminism sources beyond `HashMap`/`HashSet` (UUIDs, background threads, atomics, environment state), and who owns the decision that a module's grading draws are adequate before content ships.

**Doubt-driven-development stop condition, named explicitly (original gate design):** stopped at three cycles (the process's own ceiling) with real findings still surfacing in the third — per the process, that is itself information: this gate design's harness-security depth is not fully closed by a pre-content design doc, and forcing a fourth cycle here would mean specifying Coachgremlin's actual test-harness implementation inside a document that explicitly isn't supposed to do that yet (see this doc's own contract boundary). The deferred list above names what's still open rather than hiding it. The real next test of this design is Coachgremlin's committed dry-run discipline (point 8: construct a wrong implementation per module, confirm the seed sets catch it) against actual code, not another round of reviewing prose.

**Doubt-driven-development stop condition, named explicitly (Phase A.8, point 2's grading-draw redesign, 2026-08-30):** stopped at three cycles (single-model cycle 1 plus independently-convergent Codex cross-model, single-model cycles 2 and 3) with a real, critical finding still surfacing in the third (grading not being bound to a clean checkout of the recorded commit) — fixed rather than deferred, since it was a correctness gap in the mechanism itself, not an implementation-level detail. What remains open after that fix is fixed in *kind*, not just unaddressed: grinding via trivial tree-changing edits, and a self-administered version-pin check's blindness to deliberate pin selection, are both named precisely in point 3 above rather than claimed closed, mirroring this document's existing sampling-blind-spot residual for the original gate design. The real next test, same as the original gate design's: Coachgremlin's committed dry-run discipline (point 8) against actual code, not a fourth round of reviewing prose.
