# Module 02 Rubric: A Single-Node Checkout Service

Shared with the learner before the attempt, per Coachgremlin's own workflow. Criteria are property-phrased (an observable fact about the finished code), not technique-named (the fix itself stated outright). Each conceptual criterion below maps to one of the governing properties from `docs/workshop-design.md`'s "The shared project: `Checkout`" section that this module owns (properties 4, 5, 6, 7, 10, plus canonicalization) - properties 1-3, 8, 9 are Raft/sharding-specific and out of scope until Modules 07-08.

## Why criterion 4 is a gate, not scored

A real, evidenced finding from this module's own dry-run process (`runs/2026-08-31-module-02-dry-run/`): `MAX_LEASE_DURATION_MS` lives in `src/checkout.rs`, the one file criterion 3 already permits the learner to edit, and the earliest version of this suite was satisfied by a constant shrunk well below its shipped value - traced, at the time, against every other test's own bounds, since nothing pinned the constant's actual value directly. Property 10's entire point - a stated maximum a client cannot request past - is silently cut to nothing if the constant itself can shrink without consequence. `max_lease_duration_is_unchanged_from_its_shipped_value` now pins the exact value (`assert_eq!(MAX_LEASE_DURATION_MS, 5 * 60 * 1000)`) directly, replacing that traced-floor argument with a direct check - checked as its own gate, not left to the rest of the suite's bounds to enforce incidentally. Note that this gate only checks the constant hasn't shrunk; whether the cap is actually *applied* to a request is a separate, scored concern (criterion 10).

## Why criteria 5-10 are scored, not gated, and why there are six of them, not three

An earlier draft of this rubric had three scored criteria, all traceable to properties 1-3 (the *replicated* clock discipline) - which this module's own header comment declares out of scope until Module 07. That draft therefore covered zero of the six in-scope governing properties this module actually owns (4, 5, 6, 7, 10, canonicalization), and left two of the in-scope ones (6 and 7) with no line of defense at all: the deterministic test suite, at the time, could not actually distinguish "caches and replays the real outcome" from "coincidentally produces the same answer by re-executing," and nothing checked that `status` was actually pure. Both gaps were closed with new tests (`a_retried_sequence_replays_the_cached_response_without_re_executing` and `a_cached_denial_replays_identically_on_retry` now advance the clock between the original call and its retry so re-execution and replay produce genuinely different answers; `status_never_mutates_or_evicts_state` checks that querying an expired resource's status doesn't destroy its generation counter or its dedup entries), but criteria exist so a learner who somehow weakens or narrows one of these specific tests doesn't get a free pass - Coachgremlin checks each property directly, matching Module 01's own precedent for its rubric's own criterion 4 (a different, module-01-specific criterion - not this rubric's criterion 4 above).

A deliberate narrowing worth naming, not glossing over: `docs/workshop-design.md`'s property 6 calls for the cached outcome to be replayed "generation-stamped." This module's `Response` type only carries a `generation` field on the `Granted` variant - `Denied` and `Returned` carry no generation at all, so a denial or a return is cached and replayed as an outcome, but never as a generation-stamped one specifically. Criterion 7 above is written to match what this module's `Response` shape actually supports (replay the exact outcome, whatever it carries), not the letter of property 6's "generation-stamped" clause for all three cases - a scope decision, not an oversight, but one a learner reading the design doc directly could reasonably be confused by if it weren't stated here.

## A real, evidenced concurrency bug this module's own reference solution had

Worth stating plainly, not just fixed silently: the first attempt at a correct reference implementation for this module's dry run had a genuine bug - the dedup check, the actual `Checkout`/`Renew`/`Return` operation, and recording the new dedup entry were three separately-locked critical sections. Two concurrent, byte-identical retries (the exact scenario deduplication exists for) could both slip past the dedup check and both execute, landing one caller a permanent `Denied` for a lease it actually holds. The fix - one lock, held for the entire operation - is now load-bearing enough to have its own test (`a_genuinely_concurrent_identical_retry_is_deduplicated_not_double_executed`, 8 racing threads sending the identical request, 200 repeated trials). A learner whose implementation reintroduces this shape (locking `resources` and a separate dedup structure independently, released between steps) should reliably fail this test in practice, not merely lose theoretical points - though, like any real-thread-scheduling race test, this is a probabilistic forcing function, not a mathematical guarantee. The two 2-thread races elsewhere in this suite (`only_one_of_two_racing_checkouts_for_the_same_resource_ever_succeeds`, `a_racing_renew_and_return_never_leave_the_resource_in_a_corrupted_state`) apply noticeably less forcing pressure than this test's 8 threads, and should be read as weaker evidence of the same kind, not an equally strong guarantee.

## Why `handle`/`status` take `now_ms` as an explicit parameter, not an internally-owned clock

A design correction found via this module's own doubt-driven-development review, before any learner ever saw an earlier internal-`Clock`-trait version of this exercise: `handle`'s output must be a pure, deterministic function of its arguments alone, because Module 07 later needs to call this exact function with a timestamp a Raft leader has already committed into the log entry being applied - a function that reads its own internally-owned clock at call time can't do that no matter how that clock is injected. Passing `now_ms` explicitly costs a single-node caller nothing (this module's own test suite just passes its own already-tracked value at each call site) and avoids a signature change Module 07 would otherwise be forced into.

## What "explain why" means for criteria 5-10

Not "the test suite passes." The learner should be able to state, in their own words: why checking `(resource, holder)` alone isn't enough for fencing (a delayed command from before a lease moved to a new generation must be rejected on the generation alone, holder aside); why a per-client-only dedup key breaks under this service's own mainline usage (a client holding two independent leases needs two independent retry histories); why a cached denial must never flip to granted on retry even once the world has genuinely changed (the client that received the denial has no way to know a retry might now succeed differently, and depends on getting the same answer); why a resource's generation counter has to survive `status` calls even against an already-expired lease (the next real `Checkout` must never reissue an already-used generation); why canonicalizing only the exclusivity check, and not the dedup key (both halves) or `status`'s own reported identifier, still leaves the door open to exactly the bypass canonicalization exists to close; and why a cap that only exists as an unshrunk constant, never actually applied to a requested duration, protects nothing at all.

## A note on this module's seedless deterministic tier

Unlike every other module in this workshop, Module 02's exercise has no simulated network - `CheckoutService` is a pure, in-memory, `Mutex`-guarded type, with nothing for `turmoil` to schedule. Its deterministic gate is therefore `cargo test`/`cargo clippy` against the fixed test suite above, not a seeded practice-set-plus-grading-draw the way Modules 01 and 03+ use. Three of this suite's 34 tests (`only_one_of_two_racing_checkouts_for_the_same_resource_ever_succeeds`, `a_racing_renew_and_return_never_leave_the_resource_in_a_corrupted_state`, `a_genuinely_concurrent_identical_retry_is_deduplicated_not_double_executed`) are a further, named exception even within that: they run real concurrent races under actual OS thread scheduling, repeated 200 times each, and are not exactly reproducible seed-to-seed the way the rest of this workshop's tests are - their confidence scales with trial count and real scheduler variance, not a seed number.
