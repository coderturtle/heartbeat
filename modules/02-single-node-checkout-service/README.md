# Module 02: A Single-Node Checkout Service

## The question this module answers

What does an exclusive-ownership API need to guarantee before I even think about replicating it?

## Where it sits in the arc

Second module. Prerequisite: [Module 01](../01-rpc-over-unreliable-network/README.md) - needs the RPC layer to expose a service at all. Next: [Module 03, Raft: Leader Election](../03-raft-leader-election/README.md) - the hinge is that Module 07 later wraps *this exact `Checkout` interface* in Raft, so a bug found there is attributable to the Raft layer, not the API, only because this module's interface was proven correct on its own first. See [`modules/README.md`](../README.md) for the full arc, why this order (including the honest note that this ordering is a debugging-attribution argument, not a hard technical dependency), and how `Checkout` is the one product this whole workshop builds.

## Learning objectives

- Implement `Checkout`'s core API - a single `handle(&Request, now_ms: u64) -> Response` entry point dispatching `Checkout`/`Renew`/`Return`, plus a separate, pure-read `status(&str, now_ms: u64) -> StatusInfo` - correct under concurrent access, with no replication involved yet. One unified dispatch for the three mutating operations, rather than three separate methods, is deliberate: Module 07 later replicates this exact call shape as a single command any consensus protocol can propose and apply uniformly. `now_ms` is a plain parameter, not read from any clock this service owns - this module's own doubt-driven-development review found that an internally-injected `Clock` trait, while fine for a single-node service, can't be the function Module 07 later calls with a timestamp a Raft leader has already committed into the log entry being applied; a caller here just passes its own clock's current reading at each call site instead. `lease_duration` is client-requested but server-capped to a stated maximum (`docs/workshop-design.md`, added cycle 2 of this design's doubt-driven-development review) - an uncapped initial grant reopens the same unbounded-hold abuse the generation/lease-expiry mechanism exists to prevent.
- Get lease expiry right without any background timer: expiry is derived purely by comparing a stored `expires_at_ms` against the `now_ms` a call was given, at the moment of *every* call that depends on it - `status` included, independently of `handle`, so an idle resource nobody has touched in a while is still correctly reported as expired the next time anything asks, and a `status` call must never itself evict or mutate anything (including an already-expired resource's own generation counter) on the way to answering. No real wall-clock reliance from the start, since Module 07 makes that a hard replication requirement later.
- Canonicalize resource identifiers once, at the API boundary, and route every downstream lookup through that same canonical value - no implicit re-parsing separate from the exclusivity check. This module's own reference scope canonicalizes whitespace only (`resource.trim()`); the stronger form (namespace/ref-style aliasing, e.g. `main` vs `refs/heads/main`) is Module 08's own concern once sharding needs a routing key derived from the same value - the transferable principle here is "canonicalize once, use everywhere," not the specific whitespace rule.
- Give every lease a generation number that `Checkout` returns to the caller and increments on each new grant; reject `Renew`/`Return` calls whose supplied generation doesn't match the resource's current one - the fencing mechanism that stops a delayed command from affecting a lease granted after the one it targeted, regardless of who's presenting it. A resource's generation counter persists even while it has no active lease - don't reset or drop it just because nothing currently holds the resource, or a later `Checkout` could reissue an already-used generation. `Renew` and `Return` both treat an expired-but-matching-generation lease the same way they treat one that's already been returned - a dead lease can't be renewed or explicitly returned back to life either way, and this module's own service does not special-case a caller re-`Checkout`-ing a resource they already hold under a fresh request as anything other than "still held" (that caller should `Renew`, not re-`Checkout`).
- Cache and replay the exact outcome (granted, denied, or returned) for a repeated request, keyed by `(client_id, resource)` and checked against `sequence` - scoped per resource, not just per client (`docs/workshop-design.md`, corrected cycle 3 of this design's doubt-driven-development review: a client holding two independent leases and renewing both concurrently needs two independent sequence counters, or the second renewal's cache entry silently clobbers the first's). This module's own dry run (`runs/2026-08-31-module-02-dry-run/`) found this exact bug class - a dedup key scoped by `client_id` alone - passes `cargo clippy` cleanly and needs a real, effect-checking test to catch at all. The same dry run found a genuine concurrency bug in its own first reference solution: checking the dedup cache, doing the real work, and recording the new cache entry as three separately-locked steps let two truly concurrent, identical retries both execute for real - the fix (one lock, held for the whole operation) is now itself a tested, load-bearing property, not just an implementation detail.
- Distinguish "this bug is in my checkout logic" from "this bug is in my replication logic" - the exact distinction Module 07 will need this module's interface to have already settled.
- Confirm the service's behavior doesn't depend on request ordering it can't guarantee - a `Renew` racing a `Return` for the same resource is the obvious case to get wrong, and a truly concurrent retry of the identical request is another, less obvious one. This module has no network layer of its own (that's Module 01's job, reused starting Module 07), so this is tested via genuinely concurrent calls under real OS thread scheduling, not `turmoil`-injected reordering - see the rubric's own note on why this is a deliberate, named exception to this workshop's usual seeded-determinism norm.

## Takeaway

An exclusive-ownership API checklist: idempotent checkout requests (including the sharper case of a same-holder re-checkout, which is denied as still-held rather than silently treated as a fresh grant), renewal-vs-return races, lease-duration tradeoffs, and what an interface needs to survive being replicated. Also packaged: a concurrency-test template (real OS-thread races, repeated-trials invariant checking) for any future module whose exercise has no simulated network to seed against.
