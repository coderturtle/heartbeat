# Coachgremlin's dry run: Module 02, A Single-Node Checkout Service

Second real content-building dry run for Heartbeat, per the same evidenced practice Module 01 used: a correct attempt and a deliberately naive, honest (non-adversarial) attempt, both against the same stubbed exercise (`fixtures/checkout/src/checkout.rs`'s `CheckoutService::canonicalize`/`handle`/`status`), both run against the same provided test suite (`fixtures/checkout/tests/module_02_checkout_service.rs`). Module 01's own retro explicitly warned not to assume its "clippy catches what tests don't" finding would generalize - this dry run checked that fresh, and it doesn't (see below).

## Step 3: Observe the attempt

**`attempt-good/`** (`diff.patch`): a straightforward, correct implementation - real `ResourceState`/`ActiveLease`/`DedupEntry` types keyed by `(client_id, resource)` for dedup and by canonical `resource` for lease state, generation fencing checked before any mutation, expiry derived lazily from the injected clock on every call (`handle` and `status` alike), lease duration capped identically on `Checkout` and `Renew`. `cargo test --test module_02_checkout_service`: 20/20 pass. `cargo clippy --tests -- -D warnings`: clean.

**`attempt-naive-client-scoped-dedup/`** (`diff.patch`): identical in every respect except the dedup map's key - `HashMap<String, DedupEntry>` keyed by `client_id` alone, instead of `HashMap<(String, String), DedupEntry>` keyed by `(client_id, resource)`. A real, honest mistake: the module's own learning objectives describe the key as "`(client_id, resource, sequence number)`" in prose, and a first-time implementer who reads "keyed by client and sequence" without weighting `resource` equally could plausibly drop it, especially since the bug is invisible for the overwhelmingly common case of a client that only ever holds one resource at a time. `cargo test`: 19/20 pass - see below for the one exception and a genuine correction that had to happen first. `cargo clippy --tests -- -D warnings`: **clean**.

## Step 3 (continued): a real, self-caught test-design bug, found before this dry run's actual finding could even surface

Running `attempt-good` against the test suite the first time surfaced **two test failures against the correct implementation** - not a bug in the reference logic, a bug in the tests themselves, caught only because a genuinely correct attempt was run through them before trusting any result:

1. `a_lease_survives_until_its_duration_elapses_then_the_resource_is_reissuable` reused the same `(client_id="bob", resource, sequence=1)` triple for two calls meant to represent two different points in time. Dedup correctly replayed the first call's cached denial for the second, since nothing about the request's identity had changed - a real property working exactly as specified, exposing that the test itself, not the implementation, was wrong. Fixed by giving the second call `sequence=2`.
2. `a_racing_renew_and_return_never_leave_the_resource_in_a_corrupted_state` fired a `Renew` (sequence 2) and a `Return` (sequence 3) concurrently under the *same* `client_id`. Depending on thread-scheduling luck, whichever call the shared `Mutex` serialized second could see the other's higher sequence already cached and correctly reject as `StaleSequence` - again the dedup mechanism working as specified, not a real concurrency bug, exposing that sequence numbers express one client's own strict retry order and can't be reused to represent two calls meant to race. Fixed by using two different `client_id`s (`alice-renewer`, `alice-returner`) for the two racing calls, decoupling the mutex-level race under test from the dedup layer's own sequencing.

Both fixes were verified against the unimplemented stub first (still 20/20 failures - the fixes didn't accidentally make anything vacuous) before re-running `attempt-good`, which then passed 20/20 cleanly.

## Step 3 (continued): the naive attempt's own bug initially went uncaught too

With the two fixes above in place, `attempt-naive-client-scoped-dedup` still passed all 20 tests on the first run - including `dedup_is_scoped_per_client_and_resource_not_client_alone`, the test specifically written to catch exactly this bug class. Inspection found the test asserted only `matches!(b, Response::Granted { .. })` on the second (cross-resource) checkout - true whether that response came from actually executing the second checkout or from replaying the first resource's identically-shaped cached grant, since both are the same enum variant. **This test was vacuous against its own named bug.**

Fixed by asserting the *effect*, not just the response shape: after the second checkout call, `service.status("repo/backend")` must report the resource genuinely held by its own caller (`"alice-backend"`) - a claim that can only be true if `do_checkout` actually ran against `repo/backend`'s own state, which a client-scoped dedup replay would have skipped entirely. Re-verified against all three states: still 20/20 on the stub-must-fail check (no regression - N/A here, since a stub failure is total by construction), 20/20 on `attempt-good`, and now **19/20 on `attempt-naive-client-scoped-dedup`**, failing exactly and only the intended test:

```
thread 'dedup_is_scoped_per_client_and_resource_not_client_alone' panicked:
repo/backend must actually be held - a dedup key scoped by client_id alone would have
replayed repo/frontend's cached response without ever executing this checkout against
repo/backend's own state
```

## Step 3 (continued): what clippy did and didn't catch

**`cargo clippy --tests -- -D warnings` is clean on both attempts.** Unlike Module 01's own finding (a `read()`-vs-`read_exact()` bug that `clippy::unused_io_amount` caught instantly, deterministically, on every run), a dedup key missing a struct field has no clippy lint that could plausibly catch it - this is a domain-logic/state-correctness bug, not a language-level footgun. **This confirms the prediction in Module 01's own retro (`runs/2026-08-29-module-01-dry-run/retro.md`)**: the "some fault classes need clippy, not tests" pattern does not generalize to this module's own bug surface. Here, the deterministic test suite is the *only* mechanism that catches anything - which makes the vacuous-test finding above more consequential than it would be if clippy offered a second, independent line of defense the way it did in Module 01.

## Takeaway

Packaged: the deterministic-tier test suite itself (`fixtures/checkout/tests/module_02_checkout_service.rs`), now verified discriminating against a real, plausible mistake rather than merely inspected. The concurrency-test pattern (racing calls under real OS thread scheduling, asserting an invariant across many repeated trials rather than relying on `turmoil`-seeded reproducibility, since a purely in-memory `Mutex`-guarded service has no simulated network for `turmoil` to schedule) is new to this workshop and worth reusing as a template for any future module whose exercise is similarly network-free.

## What this dry run is and isn't evidence of

**Is:** confirmation that Module 02's exercise, test suite, and rubric are real and internally consistent - a correct attempt passes everything, a real, honest wrong attempt fails at least one gate criterion, and the *reason* it fails is understood and documented.

**Is also:** direct, first-time confirmation of Module 01's own retro instruction to check "clippy vs. tests" fresh rather than assume it generalizes - it doesn't, and knowing that in advance would have been guessing, not evidence. Worth continuing to check this per module rather than converging on a rule after only two data points.

**Is also, more pointedly:** two real, load-bearing bugs found in this dry run's own test-authoring process, not in the exercise or its reference solution - a test that would have falsely failed a genuinely correct implementation (the sequence-reuse and mixed-client-id issues), and a test that would have falsely passed a genuinely buggy one (the vacuous `matches!`-only dedup check). Both were only caught by actually running both a correct and an incorrect real implementation through the suite before trusting it - exactly the discipline this dry-run process exists to enforce, and exactly why "the tests look right on inspection" is not a substitute for running them against real code.

**Isn't:** evidence that concurrency bugs in general are hard to test deterministically in this workshop - only that *this* module's exercise has no simulated network to seed against, unlike every other module in the arc; Modules 03+ return to `turmoil`-seeded determinism once real RPC/replication is back in scope.

**Isn't:** a new, independent data point toward Coachgremlin's 3-run Review Trigger (that bar counts distinct workshops, not modules within one) - but it is real, second-time evidence for this workshop's own dry-run discipline catching real problems before a learner ever sees them.

## Addendum: a doubt-driven-development pass on the exercise, tests, and rubric themselves - found this dry run was not enough

Everything above was written and the resulting PR opened without ever putting the exercise, test suite, and rubric in front of a fresh adversarial reviewer - a real process gap, caught only because a direct question was asked about whether doubt-driven-development had actually been run on this module (it had been run on Module 08's *design* in `heartbeat-private/`, but not on this module's *content*). A single-model review, given the stub, the full test suite, the rubric, and `docs/workshop-design.md`'s governing properties as its artifact and contract, found the dry run above - while real and correctly executed on its own terms - was not sufficient. Concrete findings, all confirmed and fixed:

**A genuine concurrency bug in the reference implementation itself.** `handle`'s dedup check, the actual operation, and the dedup insert were three separately-locked critical sections (two `Mutex`es, each acquired and released independently). Two truly concurrent, byte-identical retries - the exact scenario deduplication exists for - could both slip past the dedup check and both execute for real, landing whichever thread's `dedup.insert` ran last as the permanently-cached outcome, even if that outcome was `Denied(HeldByOther)` for a lease the client actually holds. The only concurrency test that could plausibly have caught this (the earlier fix for the client-id mixup, see the main record above) used *different* client IDs for its two racing calls, which correctly fixed that test's own bug but removed the one piece of coverage that would have caught this one, and nothing replaced it. Fixed by moving both `resources` and `dedup` behind one `Mutex<ServiceState>`, held for the entire `handle` call - one atomic "check, execute, record" unit, matching `on_install_snapshot`-style discipline this same factory has already converged on elsewhere. A new test, `a_genuinely_concurrent_identical_retry_is_deduplicated_not_double_executed` (8 racing threads sending the identical request, 200 trials), verifies the fix directly.

**Several tests passed under real, plausible bugs**, confirmed by tracing concrete falsifying implementations for each:
- Property 6 (exact replay) had no effective test - every "replay" test ran at unchanged clock/state, so an idempotent-re-execution implementation (not real caching) passed identically. Fixed by advancing time between the original call and its retry in both replay tests, so re-execution and replay now produce genuinely different, distinguishable answers.
- The lease-duration-cap test only exercised `now = 0`, where "cap the duration, then add to now" and "clamp the resulting timestamp to the constant" are indistinguishable - the latter means every lease granted after `t = 300_000` is born already-expired. Fixed by testing at a large nonzero `now`.
- Deny-path tests (`renew_from_the_wrong_holder...`, `return_with_wrong_generation_or_holder...`) never checked that the resource's state was left untouched - a mutate-then-validate ordering bug would have passed. Fixed by asserting the lease is unchanged after each denial.
- `status`'s purity was unenforced, and the rubric's own wording for what became criterion 6 (in the pre-review draft) contradicted the stub's own stated purity requirement. A lazy-evict-on-read implementation would destroy a resource's generation counter and still pass every prior test. Fixed with `status_never_mutates_or_evicts_state`, and the rubric's contradictory wording removed.
- `Return` on an expired-but-matching-generation lease was unspecified, and the reference implementation itself silently contradicted the stub's own doc comment about it (which said `Renew`/`Return` both treat this as `NotHeld`). Fixed by adding the same expiry check to `do_return` that `do_renew` already had, and pinning it with `return_on_an_expired_lease_is_not_held`.
- Same-holder re-checkout (a caller re-`Checkout`-ing a resource they already hold, under a fresh sequence) was unspecified and arguably contradicted this module's own README ("idempotent checkout requests"). Resolved as a real design decision, not left ambiguous: idempotency here comes entirely from the dedup mechanism (an exact-sequence retry), not from a same-holder special case in the exclusivity check itself - a caller who wants to keep a lease alive calls `Renew`. Pinned by a new test and stated explicitly in both the stub's doc comments and the README.
- Fencing's own headline scenario - a delayed command carrying a generation that a *different* client's lease has since superseded - was never actually tested; the existing tests only covered a future generation and a wrong-holder-same-generation case. Added `a_delayed_command_against_a_superseded_generation_is_denied_not_honored`.
- The concurrent renew-vs-return test had a latent, scheduling-dependent ambiguity: depending on which call won the race, a renew against a since-returned resource had no independently-pinned expected reason. Added a deterministic complement, `renew_after_the_resource_has_been_returned_is_not_held`, so the racing test's own assertion is now backed by an unambiguous, separately-verified semantic rather than an assumption.
- `canonicalize` itself was never called by any test - a learner could leave it as `todo!()` entirely, inline `.trim()` at each call site, and still pass every test that existed at the time. Added a direct unit test, plus a test proving the *dedup key* (not just the exclusivity check and `status`) is canonicalized, and a `StatusInfo::resource`-reports-the-canonical-form assertion.
- The generation counter's scope (per-resource vs. one global counter) was implied but never pinned. Added `generation_counters_are_independent_per_resource`.

**The API shape itself had real friction for Module 07** that a small, cheap change avoids entirely: `handle`/`status` read an internally-injected `Clock` trait, but Module 07 needs to call this exact function with a timestamp a Raft leader has already committed into the log entry being applied - an internal clock read, however it's injected, can't receive that. Fixed by changing both functions to take `now_ms: u64` as a plain, explicit parameter and removing the `Clock` trait from this module's public surface entirely - simpler for a learner to implement (no trait, no generic parameter on `CheckoutService`), and it costs nothing at this module's own single-node scope, since a caller just passes its own clock's current reading at each call site. This also resolved a smaller, related finding (`canonicalize` being an associated function on a generic `impl<C: Clock> CheckoutService<C>`, unusable by a future caller with no `Clock` to name, now moot since `CheckoutService` isn't generic anymore) and added `Serialize`/`Deserialize` derives to the request/response types, matching the convention Module 01's own `rpc.rs` already established, since a type that can't serialize can't cross a Raft log later without a breaking change to this already-graded file.

**The rubric covered one of six governing properties.** Rewritten to map five scored, conceptual criteria onto the five it had been missing (properties 4, 5, 6, 7, and canonicalization), with the two criteria that had actually been testing properties 1-3 (out of scope for this module) removed. Also fixed: criterion 4 (the old numbering)'s wording dropped property 5's boundedness requirement (an unbounded table keyed by every sequence ever seen would have satisfied the literal criterion text); `MAX_LEASE_DURATION_MS` living in the one file a learner may edit, with every existing test satisfied by a value as low as `1_000`, had no anti-gaming criterion at all - added one; and the Stop condition referenced a "practice set and grading draw" that doesn't exist for this seedless module, contradicting `docs/workshop-design.md`'s own >=50-seed floor policy for modules that do have one - reworded to state plainly that this module's deterministic tier has no seeded draw, the fixed test suite is the whole gate.

All fixes re-verified end to end: the full 30-test suite fails completely against the unimplemented stub (still no vacuous tests), a corrected reference implementation (fixing the concurrency bug above) passes 30/30 with `cargo clippy --tests -- -D warnings` clean, and an otherwise-identical client-scoped-dedup naive attempt fails exactly the one intended test (29/30) with clippy still clean - the same clean discrimination as the original dry run, now resting on a materially more complete test suite.

**What this addendum is evidence of, beyond the original dry run's own claims:** doubt-driven-development applies to authored *content* - an exercise, its test suite, its rubric - not only to upfront system design. A test suite that looks complete on inspection, and that a dry run's own two attempts pass and fail exactly as expected, can still have real, load-bearing gaps a fresh adversarial reader finds by asking "does this test actually verify the effect it claims to, under every plausible implementation, not just the two this dry run happened to write." The original dry run's own two-attempt methodology is necessary but was not, on its own, sufficient here.

## Addendum 2: a second doubt-driven-development cycle, run against the cycle-1 fixes themselves

Cycle 1 above found real gaps and fixed them; the user then asked, deliberately, for a second fresh-context review of the *result* rather than assuming one pass was enough - the same discipline the first addendum names ("a fresh adversarial reader... not just the two this dry run happened to write") applied recursively to cycle 1's own output. A second single-model reviewer, given the post-fix stub, the now-30-test suite, the rewritten rubric, and the same governing-property contract, found further real issues:

**`DenyReason::HeldByOther` was misleadingly named.** The variant is also returned when the *same* holder re-`Checkout`s a resource they already hold (the deliberate same-holder-recheckout design decision from cycle 1) - "held by other" is simply false in that case. Fixed by renaming the variant to `Held` everywhere (stub, tests, doc comments), with an explicit doc comment stating it covers both the other-holder and same-holder cases. A related, adjacent finding: `DenyReason::StaleGeneration` silently conflates two distinct causes (a generation that's been superseded, and a generation that matches but a wrong holder is presenting it) into one rejection category - not a bug, since fencing genuinely doesn't need to distinguish them, but undocumented as a deliberate choice until this cycle. Fixed with an explicit doc comment.

**Serde coverage was incomplete and completely unverified.** `StatusInfo` and `HeldInfo` were missing `Serialize`/`Deserialize` derives entirely (only the four request/response-path types added in cycle 1 had them), and nothing in the suite actually exercised serialization on any type - a learner could delete every derive macro on every public type and still pass all 30 tests, silently reopening the exact Module-07-crosses-a-Raft-log friction cycle 1's fix was supposed to close. Fixed by adding the derives to both types and adding `every_public_type_actually_serializes`, a real `serde_json::to_string`/`from_str` round-trip test covering all six public types.

**`canonicalize` didn't cover `client_id`, only `resource`, despite the dedup key using both.** Cycle 1's fix scoped dedup by `(client_id, resource)`, but only `resource` was ever passed through `canonicalize` - two requests differing only in `client_id`'s incidental whitespace would dedup-scope as different clients, defeating the same canonicalization guarantee cycle 1 had just finished establishing for `resource`. Fixed by canonicalizing both halves of the dedup key (documented in `canonicalize`'s own doc comment, which also now explicitly states `holder` is deliberately *not* canonicalized - a raw client-supplied identity, not a routing key), and pinned with `dedup_key_canonicalizes_client_id_too_not_just_resource`.

**`status_never_mutates_or_evicts_state` (cycle 1's own new test) only checked half of what it claimed.** It asserted the generation counter survived a `status` call but never checked the dedup table - a `status` implementation that evicted stale dedup entries as a side effect (a plausible "helpful" optimization) would have passed a test literally named for ruling that out. Strengthened to also assert a dedup entry survives an intervening `status` call.

**Property 6's third case - a cached `Return` - was untested.** Cycle 1's replay fix covered `Granted` and `Denied` replay explicitly but never added a `Returned`-replay test, leaving one of the three outcome kinds the property actually names completely unverified. Added `a_cached_return_replays_identically_on_retry`.

**Two literal-format-string bugs, introduced by cycle 1's own fixes.** `.expect("trial {trial}: ...")` doesn't interpolate - `.expect` takes a plain `&str`, not a format-macro invocation - so both new concurrency-test failure messages would have printed the literal text `{trial}` instead of the actual failing trial number, undermining exactly the debuggability the added detail was meant to provide. Fixed by converting both to `.unwrap_or_else(|| panic!("trial {trial}: ..."))`.

**Two doc-comment claims were subtly wrong.** `handle`'s doc comment called it "a pure, deterministic function of its arguments alone," which ignores that the service's own accumulated state (which the dedup mechanism depends on) is also a legitimate, necessary input - reworded to acknowledge state as an input rather than claim purity it doesn't have. Separately, `now_ms` monotonicity (that callers won't pass a *smaller* value than a prior call) was an unstated caller obligation nothing enforced or even mentioned - added an explicit doc comment that this service does not enforce it.

**The rubric's own anti-gaming evidence had gone stale from cycle 1's own fix.** Cycle 1's rubric rewrite justified the `MAX_LEASE_DURATION_MS`-unchanged gate by citing a traced floor value (as low as `1_000`) the existing suite couldn't distinguish from the real constant - but cycle 1's own new `renew_from_the_wrong_holder...` state-unchanged assertion (`expires_at_ms == 60_000` in that test) had already raised the actual traceable floor to `60_000`, silently making the rubric's own cited number wrong. Rather than re-trace and re-cite a new floor (which the next fix could just as easily stale out again), added `max_lease_duration_is_unchanged_from_its_shipped_value`, which pins the constant's exact value directly (`assert_eq!(MAX_LEASE_DURATION_MS, 5 * 60 * 1000)`) - a mechanism that can't go stale the way a traced-floor argument can. Also added a new scored criterion (10) for whether the cap is actually *applied* to a requested duration, since the gate only ever checked the constant hadn't shrunk, never that `handle` uses it.

**The rubric had a self-contradictory narrative and an ambiguous cross-reference.** It said the pre-cycle-1 rubric's three scored criteria (all mapping to properties 1-3) "covered one of six in-scope governing properties," which doesn't follow - properties 1-3 are the out-of-scope replicated-clock discipline, so a draft that only scored against them covered *zero* of the six properties this module actually owns, not one. Fixed. Separately, "matching Module 01's own precedent for its criterion 4" was ambiguous with this rubric's own criterion 4 (`MAX_LEASE_DURATION_MS`), a different criterion entirely - disambiguated with an explicit parenthetical.

**Property 6's "generation-stamped" clause is only partially met, undocumented.** `docs/workshop-design.md` calls for the cached outcome to be replayed "generation-stamped," but this module's `Response` type only carries a `generation` field on `Granted` - `Denied` and `Returned` carry none. A deliberate scope decision (criterion 7 is written to match what `Response` actually supports), but nowhere stated as such until this cycle. Added an explicit remark to the rubric.

**The 8-thread concurrency test's "will fail this test" claim overstated its own certainty**, and didn't distinguish itself from the suite's two weaker 2-thread races. Real-thread-scheduling races are a probabilistic forcing function, not a guarantee, regardless of thread count or trial count - softened the wording and explicitly noted the two 2-thread tests apply less forcing pressure than the 8-thread/200-trial one, so they're weaker (not equal) evidence of the same kind.

**A mechanical clippy bug in the stub, found only by actually running clippy, not by either review cycle.** Both DDD cycles were deliberately pure read-and-reason reviews (told explicitly not to build or run `cargo`), so neither could have caught this: the `client_id`-canonicalization doc comment cycle 2 added to `canonicalize`, and the pre-existing `Held` doc comment, each wrapped a line to start with `- ` mid-sentence, which `clippy`'s `doc_lazy_continuation` lint parses as an improperly-indented markdown list continuation - `cargo clippy --tests -- -D warnings` failed to even compile the stub, 10 of its errors from exactly these two comment blocks. Fixed by rewording both to avoid a line-leading `- ` (reflowing the sentence structure, not changing the doc comment's actual claims). Serves as a concrete instance of why the dry-run's own mechanical verification step (build both attempts, run the real gates) still matters even after a thorough prose-and-reasoning review cycle - a review that's explicitly forbidden from running the tool that would have caught this by construction.

All fixes re-verified end to end, using regenerated `attempt-good`/`attempt-naive` reference implementations (rebuilt from cycle 1's scratch copies, with every cycle-2 fix applied - `Held` rename, both-halves dedup-key canonicalization, added derives): the full 34-test suite fails to build zero errors and shows exactly 2 tests passing against the unimplemented stub (`every_public_type_actually_serializes` and `max_lease_duration_is_unchanged_from_its_shipped_value` - both legitimate, since neither calls `canonicalize`/`handle`/`status`, the only `todo!()`-stubbed functions; the other 32 fail as expected). A corrected reference implementation passes 34/34 with `cargo clippy --tests -- -D warnings` clean; an otherwise-identical client-scoped-dedup naive attempt fails exactly the one intended test (33/34), clippy still clean - the same clean discrimination as both prior verifications, now against a materially more complete suite. `diff.patch` for both attempts regenerated against the current stub.

**What this second addendum is evidence of:** a single doubt-driven-development cycle is not self-certifying just because it found and fixed real things - the fixes themselves can introduce new gaps (the format-string bug, the stale anti-gaming evidence) or leave a fix half-applied (dedup-key canonicalization covering only one of two halves it needed, the purity test covering only one of two structures it named). Running a second cycle against cycle 1's own output, rather than treating "we already did doubt-driven-development on this" as done, is what caught these - consistent with this skill's own stop condition (stop when a cycle returns only trivial findings, not after a fixed number of cycles regardless of what they find). This cycle's findings were substantive, not trivial, so a third cycle was considered; see `retro.md` for the go/no-go reasoning.
