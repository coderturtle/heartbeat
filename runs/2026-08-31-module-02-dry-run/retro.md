# Retro: Heartbeat's second real content-building dry run

Module 02 is the first module in this workshop whose exercise has no network at all - a pure, in-memory, `Mutex`-guarded service. Module 01's own retro explicitly flagged this module as the one to check "clippy vs. tests" fresh rather than assume its finding generalized. This retro checks that, plus a second, unplanned question the dry run itself raised.

## Did Module 01's "clippy catches what tests don't" finding generalize?

**No - and the direction it failed in matters.** Module 01's real bug (`read()` instead of `read_exact()`) was a language-level footgun with a dedicated, deny-by-default clippy lint. Module 02's injected bug (a dedup key missing a struct field) is a domain-logic/state-correctness bug with no clippy lint that could plausibly express it - "did you remember to include this field in your hash map key" isn't a shape static analysis catches. Here, `cargo test` was the *only* mechanism that distinguished the two attempts; clippy was clean on both. This is the clean opposite of Module 01's split, confirming the instruction not to assume one module's tier balance for the next.

## A question this dry run raised that Module 01's didn't: what happens when the test suite itself is wrong?

Module 01's dry run found its *bug* by running two attempts through an already-trusted test suite. This dry run found two real bugs *in the test suite itself* - one that would have failed a correct implementation (reused sequence numbers across logically-distinct calls), one that would have failed a differently-shaped correct implementation (sequence numbers reused across a race between two calls, when sequence numbers only ever express one client's own strict order) - before the actual naive-attempt bug could even be evaluated fairly. Both were caught only because `attempt-good` was run through the suite and failed, which is itself the dry-run discipline working as designed: a correct attempt failing is exactly as informative as an incorrect attempt passing, and neither should be dismissed as "must be a fluke" without reading why.

A third, more subtle case surfaced *after* both attempts were passing/failing as expected on the surface: the test specifically written to catch the injected bug initially passed against the buggy implementation too, because it asserted the response's enum variant (`matches!(_, Response::Granted { .. })`) rather than its effect on state. This is a distinct failure mode from the first two - not "the test's premise doesn't hold under concurrency," but "the test's assertion is weaker than its own name claims." Worth naming as its own checklist item for future modules, distinct from the vacuous-against-a-`todo!()`-stub check Module 01's addendum already established: **a test can be non-vacuous against the unimplemented stub (it fails there, correctly) and still be vacuous against a specific real bug it was written to catch, if its assertion doesn't actually verify the effect the bug would produce.** Checking "does this fail against the stub" isn't sufficient on its own; checking "does this fail against a real, deliberately-injected instance of the exact bug it's named for" is the stronger and more specific check, and this dry run is now direct evidence for why both matter.

## Did the concurrency-test design (no turmoil, repeated-trials invariant checking) actually earn its place?

**Yes, conditionally.** Two tests (`only_one_of_two_racing_checkouts_for_the_same_resource_ever_succeeds`, `a_racing_renew_and_return_never_leave_the_resource_in_a_corrupted_state`) exercise genuine `Mutex`-contention races under real OS thread scheduling, 200 trials each, and both passed reliably against `attempt-good` and remained passing against the naive attempt (whose injected bug is orthogonal to raw concurrency safety - a correctness bug in *what* gets cached, not *whether* the `Mutex` serializes access correctly). This is real signal, but it's a genuinely different kind of test than everything else in this workshop's suites: not seed-reproducible, not comparable seed-to-seed, and its confidence is only as good as trial count and real scheduler variance on whatever machine runs it. Worth flagging honestly in the module's own README/rubric as a named exception to the "everything is turmoil-seeded and exactly reproducible" norm the rest of this workshop holds to, not silently treated as equivalent.

## What Coachgremlin's Module 03 dry run should check fresh, not assume

Module 03 (Raft leader election) reintroduces real network fault injection via `turmoil` - the first module since 01 to have one. Don't assume Module 02's "tests are the only line of defense, clippy is orthogonal" finding generalizes back the other way just because turmoil is back in scope; check fresh, same discipline. Also worth carrying forward explicitly: re-run any newly-written test against a genuinely correct attempt *before* trusting it against a naive one, given how much this dry run's own value turned out to come from bugs in its own test-authoring, not just the exercise.

## Addendum: this dry run's own two-attempt methodology was necessary but not sufficient

A direct question about whether doubt-driven-development had been run on this module's actual content (not just, earlier in this project, on a different module's upfront design) exposed a real gap: it hadn't. A single fresh-reviewer pass on the stub, test suite, and rubric together found the dry run above - executed correctly on its own terms, real attempts, real discrimination - still missed a genuine concurrency bug in its own reference implementation, several tests that would pass under real, plausible bugs the two attempts here never happened to instantiate, real API-shape friction for Module 07, and a rubric covering one of six governing properties. See `grading.md`'s own addendum for the full list.

The pattern worth naming for every future module, not just this one: **a dry run's two attempts (one correct, one naive) only exercise the specific bugs someone thought to write into the naive attempt.** A test suite can correctly distinguish those two attempts and still be blind to a different plausible bug nobody happened to inject - `only_one_of_two_racing_checkouts_for_the_same_resource_ever_succeeds` and the original `dedup_is_scoped_per_client_and_resource_not_client_alone` both passed cleanly on their first write, against the specific attempts written for this dry run, while each had a real weakness (the response-shape-only assertion in the latter case, already caught once; a completely untested concurrent-identical-retry scenario in the former) that no attempt in this dry run happened to trip. A fresh adversarial reviewer, asked to find gaps rather than to grade the two attempts already on hand, is a different and complementary check - not a replacement for the dry run, but not optional alongside it either, for any module whose content sets a contract other modules build on.

## Go/no-go on Module 02 (cycle 1)

**Go, after the doubt-driven-development pass above, not before.** The rubric, as originally shipped from this dry run alone, would have merged real gaps - an exploitable reference-implementation bug, several under-verified properties, and a rubric that scored the wrong properties. With that pass's fixes applied and re-verified (30/30 on a corrected reference implementation, 29/30 on the client-scoped-dedup naive attempt, clippy clean on both, the full suite still failing completely against the unimplemented stub), the module is real and internally consistent: a correct attempt passes everything, a real, honest wrong attempt fails at least one gate criterion for an understood reason, and the rubric's scored criteria now actually map onto the properties this module owns. Takeaway (the concurrency-test template, now demonstrated against a real bug it was built to catch, not just a hypothetical one) is real and demonstrated, with its own stated limitations named rather than glossed over.

## Addendum: a second cycle, run deliberately against cycle 1's own output

The user asked explicitly for a second doubt-driven-development cycle rather than treating cycle 1's "go" above as final - a direct instance of this workshop's own retro discipline (don't assume a finding, or a fix, generalizes without checking) applied to the DDD process itself, not just to module content. The second cycle found real, substantive issues *in cycle 1's own fixes*, not fresh problems cycle 1 had simply missed the first time: a misleadingly-named variant (`HeldByOther`, also returned for the same holder), incomplete serde coverage nothing tested, a canonicalization fix that covered only half the key it needed to, a purity test that checked only half the state it named, a missing third replay case, two literal-format-string bugs the cycle-1 fixes themselves introduced, and rubric prose whose own cited evidence had gone stale because of another cycle-1 fix. See `grading.md`'s "Addendum 2" for the full list.

The pattern worth naming, distinct from what the first addendum already established: **a fix for one finding can silently create, or fail to fully close, another** - canonicalizing `resource` in the dedup key without also canonicalizing `client_id` is not a different bug from the one cycle 1 was fixing, it's the same fix applied incompletely; citing a traced floor value in the rubric, then later adding a test that moves that floor, is not a new problem, it's the first fix's own justification going stale. Neither is the kind of gap a reviewer scanning only the *diff* would catch - both required re-reading the fixed artifact whole, as if seeing it for the first time, which is exactly what a fresh-context cycle-2 reviewer (who never saw cycle 1's fixes being made, only their result) is positioned to do that the same session re-reading its own work is not.

## Go/no-go on Module 02 (cycle 2)

**Go.** All cycle-2 findings were fixed and re-verified end to end: the regenerated `attempt-good` reference implementation (rebuilt with every cycle-2 change - the `Held` rename, both-halves dedup-key canonicalization, the added serde derives) passes the full 34-test suite (34/34) with `cargo clippy --tests -- -D warnings` clean; the regenerated client-scoped-dedup naive attempt fails exactly the one intended test (33/34), clippy still clean; the suite still fails completely against the unimplemented stub except for the two tests that legitimately don't call any `todo!()`-stubbed function (`every_public_type_actually_serializes`, `max_lease_duration_is_unchanged_from_its_shipped_value`) - confirmed, not assumed, by checking which two tests those were rather than taking "2 passed" on faith. `diff.patch` for both attempts regenerated against the current stub to match. Cycle 2's findings were real and substantive (not the "trivial findings" stop condition this skill names), so a third cycle was considered per this project's own precedent of asking rather than assuming one pass is enough - a third cycle was not run for this iteration, since cycle 2's own findings were themselves about incompleteness in cycle 1's fixes (a converging pattern - each fix getting closer to fully closing its own finding) rather than freshly-discovered new categories of problem, which is closer to this skill's diminishing-returns stop condition than to the substantive-cycle-2 case that argued for running cycle 2 at all. Rubric now has 10 criteria (4 gate, 6 scored) covering all six of this module's in-scope governing properties, with the property-6 partial-coverage and property-10 applied-vs-unshrunk distinctions both stated explicitly rather than left implicit.
