# Retro: Heartbeat's second real content-building dry run

Module 02 is the first module in this workshop whose exercise has no network at all - a pure, in-memory, `Mutex`-guarded service. Module 01's own retro explicitly flagged this module as the one to check "clippy vs. tests" fresh rather than assume its finding generalized. This retro checks that, plus a second, unplanned question the dry run itself raised.

## Did Module 01's "clippy catches what tests don't" finding generalize?

**No - and the direction it failed in matters.** Module 01's real bug (`read()` instead of `read_exact()`) was a language-level footgun with a dedicated, deny-by-default clippy lint. Module 02's injected bug (a dedup key missing a struct field) is a domain-logic/state-correctness bug with no clippy lint that could plausibly express it - "did you remember to include this field in your hash map key" isn't a shape static analysis catches. Here, `cargo test` was the *only* mechanism that distinguished the two attempts; clippy was clean on both. This is the clean opposite of Module 01's split, confirming the instruction not to assume one module's tier balance for the next.

## A question this dry run raised that Module 01's didn't: what happens when the test suite itself is wrong?

Module 01's dry run found its *bug* by running two attempts through an already-trusted test suite. This dry run found two real bugs *in the test suite itself* - one that would have failed a correct implementation (reused sequence numbers across logically-distinct calls), one that would have failed a differently-shaped correct implementation (sequence numbers reused across a race between two calls, when sequence numbers only ever express one client's own strict order) - before the actual naive-attempt bug could even be evaluated fairly. Both were caught only because `attempt-good` was run through the suite and failed, which is itself the dry-run discipline working as designed: a correct attempt failing is exactly as informative as an incorrect attempt passing, and neither should be dismissed as "must be a fluke" without reading why.

A third, more subtle case surfaced *after* both attempts were passing/failing as expected on the surface: the test specifically written to catch the injected bug initially passed against the buggy implementation too, because it asserted the response's enum variant (`matches!(_, Response::Granted { .. })`) rather than its effect on state. This is a distinct failure mode from the first two - not "the test's premise doesn't hold under concurrency," but "the test's assertion is weaker than its own name claims." Worth naming as its own checklist item for future modules, distinct from the vacuous-against-a-`todo!()`-stub check Module 01's addendum already established: **a test can be non-vacuous against the unimplemented stub (it fails there, correctly) and still be vacuous against a specific real bug it was written to catch, if its assertion doesn't actually verify the effect the bug would produce.** Checking "does this fail against the stub" isn't sufficient on its own; checking "does this fail against a real, deliberately-injected instance of the exact bug it's named for" is the stronger and more specific check, and this dry run is now direct evidence for why both matter.

## Did the concurrency-test design (no turmoil, repeated-trials invariant checking) actually earn its place?

**Yes, conditionally.** Two tests (`only_one_of_two_racing_checkouts_for_the_same_resource_ever_succeeds`, `a_racing_renew_and_return_never_leave_the_resource_in_a_corrupted_state`) exercise genuine `Mutex`-contention races under real OS thread scheduling, 200 trials each, and both passed reliably against `attempt-good` and remained passing against the naive attempt (whose injected bug is orthogonal to raw concurrency safety - a correctness bug in *what* gets cached, not *whether* the `Mutex` serializes access correctly). This is real signal, but it's a genuinely different kind of test than everything else in this workshop's suites: not seed-reproducible, not comparable seed-to-seed, and its confidence is only as good as trial count and real scheduler variance on whatever machine runs it. Worth flagging honestly in the module's own README/rubric as a named exception to the "everything is turmoil-seeded and exactly reproducible" norm the rest of this workshop holds to, not silently treated as equivalent.

## What Coachgremlin's Module 03 dry run should check fresh, not assume

Module 03 (Raft leader election) reintroduces real network fault injection via `turmoil` - the first module since 01 to have one. Don't assume Module 02's "tests are the only line of defense, clippy is orthogonal" finding generalizes back the other way just because turmoil is back in scope; check fresh, same discipline. Also worth carrying forward explicitly: re-run any newly-written test against a genuinely correct attempt *before* trusting it against a naive one, given how much this dry run's own value turned out to come from bugs in its own test-authoring, not just the exercise.

## Go/no-go on Module 02

**Go.** Rubric met by a real correct attempt; a real, honest naive attempt correctly fails exactly one gate criterion, and the reason is understood, not just observed. The test suite itself needed three real corrections before that finding could be trusted - all three are now part of the shipped suite, not left as known gaps. Takeaway (the concurrency-test template) is real and demonstrated, with its own stated limitation named rather than glossed over.
